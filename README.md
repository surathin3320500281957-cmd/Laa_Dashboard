## 1. ภาพรวมไฟล์และการ mapping กับ sheet ต้นฉบับ (สำคัญที่สุด — อ่านก่อนแก้อะไร)

ไฟล์เดียว `index.html` — HTML + CSS + JavaScript (Chart.js) ไม่มี backend, ข้อมูลทั้งหมด**ฝังอยู่ในไฟล์เป็น JSON literal** (3 ตัวแปรหลัก: `AF`, `NA`, `MN`)

**แต่ละแท็บมีที่มาจากคนละ sheet ใน Excel ต้นฉบับ — ⚠️ NA และ MN ไม่ได้ derive จาก AF:**

| แท็บ | ตัวแปรใน JS | ที่มาจริง | ความสัมพันธ์กับ AF |
|---|---|---|---|
| 1. ภาพรวม | `AF` | Sheet **AF** (116 คอลัมน์) | เป็น array หลัก |
| 2. ไม่ดำเนินการ(ภาพรวม) | `OVNA` | `= AF.filter(status==='ไม่ดำเนินการ')` | **derived จาก AF จริง** — รับประกัน 100% ว่า `update` ไม่มีวันอยู่ใน 11 สถานะเลย |
| 3. ไม่ดำเนินการ(สคล/สคจ ชี้แจง) | `NA` | Sheet **สำหรับกรอง-ตรวจสอบ** (163 แถว) | **array แยก, ไม่ใช่ filter จาก AF** — ดู 1.1 |
| 4. ไม่ดำเนินการ(ข้อมูลหน่วยงานอื่น) | `MN` | Sheet **รายเดือน-ชน** (151 แถว) | **array แยก** — ดู 1.1 |

### 1.1 วิธีสร้าง NA และ MN (สำคัญ — ต้องทำแบบนี้ทุกครั้งที่อัปเดตข้อมูล)

**ทั้งคู่ยึดจำนวนแถว/รายชื่อลูกค้าจาก sheet ต้นทางของตัวเอง ไม่ใช่ filter จาก AF:**

```
NA:  วนทุกแถวใน "สำหรับกรอง-ตรวจสอบ"
     → ถ้ารหัสลูกค้าพบใน AF: copy record ทุกฟิลด์จาก AF ตรงๆ
     → ถ้าไม่พบใน AF (ลูกค้าหลุดออกจากระบบไปแล้ว เช่น ส่งมอบแล้ว):
       ใช้ฟิลด์พื้นฐานจาก "สำหรับกรอง-ตรวจสอบ" เอง (dept/bp/proj/house/cust_name/
       change_status/confirm_flag), update = ปรับสรุปการUPDATE, ฟิลด์อื่นเว้นว่าง

MN:  วนทุกแถวใน "รายเดือน-ชน" ด้วยหลักการเดียวกัน (ใช้ "รหัสลูกค้า" คอลัมน์กับ
     "ปรับสรุปการUPDATE" คอลัมน์แทน) — ค่า guarantee คงที่ = "หลังค้ำประกัน" สำหรับ
     กลุ่มที่ไม่พบใน AF
```

⚠️ **ผลที่ตามมา:** เพราะ "สำหรับกรอง-ตรวจสอบ"/"รายเดือน-ชน" เป็น list ที่สาขากรอกเอง อาจ**ล้าหลัง**กว่า AF จริง — บางคนใน list นี้อาจ**ขยับไปสถานะซ่อมจริงใน AF แล้ว** (progress ไปแล้วแต่ยังไม่ได้ลบออกจาก list ชี้แจง) ทำให้ **NA/MN มี record ที่ `update` อยู่ใน 11 สถานะจริงปนอยู่ด้วย** (ไม่ใช่แค่ "ไม่ดำเนินการ" ล้วนๆ เหมือน OVNA) — ตรวจสอบล่าสุด (18-08-69): NA มี 39/163, MN มี 36/151 ที่ progress ไปแล้ว

**สรุปสั้นๆ:** OVNA เท่านั้นที่รับประกันว่าไม่มีสถานะจริงปนอยู่ (เพราะ derive จาก AF ตรงๆ) — **NA และ MN ต้องแก้ไขด้วย logic เดียวกับ AF ทุกจุดที่เกี่ยวกับสถานะซ่อม** (ดูหัวข้อ 4)

**ขนาดข้อมูล ณ ชุดล่าสุด (18-08-69):** AF 1,021 | OVNA 143 | NA 163 | MN 151

## 3. ⚠️ ลักษณะพิเศษของข้อมูลดิบ — "รูปแบบล้ำหน้า 1 สถานะ" (พบ 4 จุด ทุกจุดแก้ไปแล้ว)

ระบบต้นทาง (AF sheet) มี pattern เดียวกันซ้ำๆ: **บันทึกวันที่/ข้อมูลของสถานะถัดไปไว้ล่วงหน้า 1 ขั้นเสมอ** แม้ `update` (สถานะทางการ) ยังไม่ขยับไปถึง — ไม่เคยล้ำเกิน 1 ขั้น ยืนยันด้วยข้อมูลจริงทุกครั้ง

| จุดที่กระทบ | ข้อมูลดิบ | ฟังก์ชันที่แก้ |
|---|---|---|
| คอลัมน์วันที่ d01-d11 | `DATE_01..11` มีวันที่ของสถานะถัดไปติดมาด้วย | `dCell(x,n)` |
| เช็คสถานะซ่อมหลังสุด | `CK_CUSTCARE_ST` ล้ำหน้า `update` ได้ 1 ขั้น | `ckStatus(x)` |
| วันค้างสถานะ | `days_lag` (จาก `MAX_STATUS_DATE`) คำนวณจากวันที่ล้ำหน้า ต่างจากจริงได้ถึง 100+ วัน | `statusLagDays(x)` |
| วันค้างสถานะซ่อมหลังสุด | `ckLagValue()` เดิม fallback ไปใช้ `days_lag` ดิบ (บั๊กเดียวกันซ่อนอยู่) | `ckLagValue(x)` (แก้ให้ fallback ไป `statusLagDays()` แทน) |

**หลักการแก้ทั้งหมด:** ถ้า `update` อยู่ใน STAGES11 (กำลังซ่อมจริง) → ใช้ข้อมูลของ**สถานะปัจจุบันเอง**เท่านั้น (ผ่าน `stageIdx(x)`) ไม่เชื่อค่าที่ "ล้ำหน้า" ไปจากสถานะปัจจุบัน ถ้าอยู่นอก STAGES11 (กลุ่มไม่ดำเนินการ) → ใช้ค่าดิบเดิมตามปกติ (ไม่มีปัญหานี้)

## 4. Logic / ฟังก์ชันหลักที่แก้ไว้แล้ว (ห้ามลบ/แก้โดยไม่เข้าใจก่อน)

ทั้งหมดอยู่ในส่วน `<script>` ประมาณบรรทัด 440-640

| ฟังก์ชัน/ค่าคงที่ | หน้าที่ |
|---|---|
| `STAGES11` / `STAGES12` | ลำดับสถานะมาตรฐาน (ห้ามสลับลำดับ) |
| `curStage(x)` | คืน `x.update` ถ้าอยู่ใน STAGES11, ไม่งั้นคืน `'ไม่ดำเนินการ'` — ใช้กับ filter/กราฟ/pivot ของ "สถานะซ่อมปัจจุบัน" |
| `stageIdx(x)` | ลำดับ (1-11) ของสถานะปัจจุบัน, คืน `0` ถ้านอก STAGES11 |
| `dCell(x,n)` | คืนค่า `d0n` เฉพาะ `n <= stageIdx(x)` ไม่งั้นคืน `'—'` |
| `ckStatus(x)` | ถ้าอยู่ใน STAGES11 → คืน `x.update` (sync ตรงเป๊ะ); ถ้าไม่ → คืน `x.ck_custcare_st_grp` |
| `statusLagDays(x)` | ถ้าอยู่ใน STAGES11 → คำนวณ `UPD_REF_DATE - d0N(สถานะปัจจุบัน)`; ถ้าไม่ → คืนค่า raw `x.days_lag` |
| `updSummary(x)` | คำชี้แจง (ปรับสรุปการUPDATE) — คืนค่าเฉพาะกลุ่มไม่ดำเนินการ, กลุ่มกำลังซ่อมคืนค่าว่าง |
| `parseDMY(str)` | แปลง `"DD/MM/YY"` (พ.ศ.) เป็น JS Date |
| `contractLagDays(x)` | (เดิม) `UPD_REF_DATE - parseDMY(x.start_con)` — **ปัจจุบันไม่ถูกใช้กรองแล้ว** ตัวกรอง "วันที่ค้างสัญญา" ใช้ `contractDateLagDays(x)` (contract_date) ให้ตรงคอลัมน์ที่แสดง |
| `ckLagValue(x)` | วันค้างสถานะซ่อมหลังสุด — ถ้า `ck_custcare_st` มีวันที่ฝัง ใช้วันนั้น; ไม่งั้น fallback ไป `statusLagDays(x)` (**ไม่ใช่** raw `days_lag`) |
| `UPD_REF_DATE` | วันที่อ้างอิงคำนวณ "วันค้าง" ทั้งหมด — **อ่านจาก `UPDATE_BANNER.date` อัตโนมัติ (ไม่ต้องแก้มืออีก)** |

### 4.1 สิ่งที่ถูกลบออกไปแล้ว (อย่าเอากลับมา)
- Dropdown filter "สถานะซ่อมถัดไป" (`ov-next`) — ลบออกจากระบบทั้งหมดแล้ว (dead code, ไม่เคยถูกใช้กรองจริง)

### 4.2 ขอบเขตการแก้ไขปัญหาข้อ 3 — ครอบคลุมกี่แท็บ
**ครอบคลุม 3 แท็บ: ภาพรวม (AF), ไม่ดำเนินการ(สคล/สคจ) (NA), ข้อมูลหน่วยงานอื่น (MN)** — ทุกจุดที่แสดง/กรองด้วยคอลัมน์ d01-d11, เช็คสถานะซ่อมหลังสุด, วันค้างสถานะ, วันค้างสถานะซ่อมหลังสุด ใน 3 แท็บนี้ต้องเรียกผ่านฟังก์ชันในหัวข้อ 4 เท่านั้น ห้ามอ่าน field ดิบตรงๆ

**แท็บ "ไม่ดำเนินการ(ภาพรวม)" (OVNA) ไม่ต้องแก้** เพราะ `= AF.filter(status==='ไม่ดำเนินการ')` รับประกันว่า `update` ไม่มีวันอยู่ใน STAGES11 เลย ทุกฟังก์ชันในหัวข้อ 4 จะ fallback ไปใช้ค่าดิบเดิมเสมอ (no-op) — **แต่ต้องตรวจสอบสมมติฐานนี้ใหม่ทุกครั้งที่อัปเดตข้อมูล** (ดูหัวข้อ 4.3)

### 4.3 ⚠️ อย่าเชื่อ "no-op" โดยไม่ตรวจสอบ
เคยเข้าใจผิดมาก่อนว่า NA/MN เป็น no-op เหมือน OVNA (เพราะตอนนั้น NA ยัง derive จาก AF.filter จริง) — พอเปลี่ยนมาใช้ sheet ต้นทางเป็นฐาน (หัวข้อ 1.1) สมมติฐานนี้ผิดทันที ทุกครั้งที่แก้โครงสร้าง NA/MN หรืออัปเดตข้อมูลใหม่ **ให้เช็คซ้ำด้วยคำสั่งนี้ก่อนตัดสินใจว่าต้องแก้ไหม:**
```js
NA.filter(r => STAGES11.includes(r.update)).length   // ถ้า > 0 ต้องใช้ฟังก์ชันหัวข้อ 4
MN.filter(r => STAGES11.includes(r.update)).length   // ถ้า > 0 ต้องใช้ฟังก์ชันหัวข้อ 4
```

### 4.4 Export Excel — `{raw:true}` ป้องกันข้อมูลเพี้ยนซ้ำ
ฟังก์ชัน `exXL(id,name)` (ใช้ร่วมกันทุกปุ่ม Export Excel ทั้ง 8 จุดในทุกแท็บ) เรียก `XLSX.utils.table_to_sheet(t,{raw:true})` — **ห้ามลบ option `{raw:true}` นี้ออก** เพราะ SheetJS จะ auto-detect เนื้อหาที่ดูเหมือนวันที่/ตัวเลข (เช่น เลขบ้าน `"2/8"`) แล้วแปลงเป็นวันที่จริงในไฟล์ที่ export ออกไป ซ้ำรอยปัญหาเดียวกับที่ Google Sheets ทำตอน import (หัวข้อ 7 ข้อ 5) — เคยทดสอบยืนยันแล้วว่าไม่มี `{raw:true}` จะเพี้ยนทันทีถ้าเจอ pattern แบบนี้ในข้อมูล แม้ ณ ตอนเขียนเอกสารนี้ข้อมูลชุดปัจจุบันจะไม่มี pattern นี้ก็ตาม

⚠️ **Trade-off ที่ต้องรู้:** เพราะบังคับทุกเซลล์เป็นข้อความ คอลัมน์ตัวเลข/เงิน (due_amt, debt, วันค้างต่างๆ) ในไฟล์ Excel ที่ export ออกไปจะเป็น**ข้อความ** ไม่ใช่ตัวเลขที่ SUM/คำนวณต่อในเซลล์ Excel ได้ทันที — ยอมรับ trade-off นี้แล้วเพราะป้องกันความเสี่ยงข้อมูลเพี้ยนแบบไม่รู้ตัวซึ่งร้ายแรงกว่า

## 5. รหัสลูกค้า + ประเภทสัญญา + Filter

เพิ่ม 2 คอลัมน์ในตารางรายละเอียดทุกแท็บ ต่อจาก "บ้านเลขที่": **รหัสลูกค้า** (`cust`, มีอยู่แล้วทุก array) และ **ประเภทสัญญา** (`contract_type`, ใหม่)

เพราะ `CONTRACT_TYPE1` มีแค่ใน sheet AF การเติม `contract_type` ให้ `NA`/`MN` ต้อง join ย้อนกลับด้วย `cust`:
```python
ct_map = {str(cust_code): contract_type1 for แต่ละแถวใน AF sheet}
for r in AF/NA/MN: r['contract_type'] = ct_map.get(str(r['cust']), '')
```
รายการที่ join ไม่เจอ (ลูกค้าหลุดจาก AF ไปแล้ว) จะแสดง "—" — เป็นเรื่องปกติ

**Filter ที่เพิ่มในทุกแท็บ (มี dropdown + chip + logic ครบ):**
- ประเภทสัญญา (`{pfx}-ctype`)
- วันค้างทำสัญญา (`{pfx}-conlag`) — bucket 0-30/31-60/61-90/เกิน 90 วัน ผ่าน `inLagRangeStrict()` (ค่า `null` ไม่ถูกนับเข้า bucket ไหนเลย ต่างจาก `inLagRange()` เดิมที่ปนค่า null เป็น 0)

**เฉพาะแท็บภาพรวมเพิ่ม:** filter "ปรับสรุปการ UPDATE" (`ov-upd`) — กรอง exact match จาก `x.update` (6 ตัวเลือกที่อยู่นอก STAGES11) วางคอลัมน์ต่อจาก "การซ่อม" ก่อน "สถานะซ่อมปัจจุบัน" — ให้เห็นคำชี้แจงจากสาขาทันทีเมื่อกรองสถานะปัจจุบัน = "ไม่ดำเนินการ" ไม่ต้องสลับแท็บ

## 6. ระบบ Filter Chip (แสดง filter ที่เลือกอยู่ ลบได้ทีละตัว)

ทุกแท็บมี chip แถวใต้ filter row แสดงเฉพาะ filter ที่มีค่า สีตามหมวดหมู่ (ม่วง=กอง/สาขา/โครงการ, น้ำเงิน=ประเภทสัญญา, เขียว=สถานะซ่อม, ส้ม=วันค้าง, แดง=สถานะ KPI เฉพาะภาพรวม)

**Config หลัก:** `OV_CHIP_CFG` (ภาพรวม) และ `otherChipCfg()` (ใช้ร่วมกัน 3 แท็บที่เหลือ, สร้าง config ผ่าน `OVNA_CHIP_CFG`/`NA_CHIP_CFG`/`MN_CHIP_CFG`) — เรียก `renderChips()` ในทุกฟังก์ชัน `ren*()` โดยอัตโนมัติ ไม่ต้องแก้ทุก `onchange` handler

**เพิ่ม filter ใหม่ → ต้องเพิ่ม chip config ด้วยเสมอ** ไม่งั้น filter จะทำงานแต่ไม่มี chip แสดง

## 7. Workflow การอัปเดตข้อมูล (Excel → Dashboard) — ขั้นตอนจริงที่เคยทำสำเร็จ

✅ **ตอนนี้มี script สำเร็จรูปแล้ว: `update_data.py`** (อยู่ใน `/mnt/user-data/outputs/` ของทุก session ที่เคยรันงานนี้ — ถ้าไม่มีให้สร้างใหม่ตาม logic ในไฟล์นี้ทั้งหมด) รวบรวม mapping + fix ทุกจุดที่เคยแก้ไว้แล้ว (coalesce update, safe_start_con, safe_yyyymmdd_or_text, sheet_status แบบไดนามิก, ฯลฯ) **ทดสอบแล้วให้ผลตรงกับ index.html ปัจจุบัน 100% ทุกฟิลด์**

**วิธีใช้:** แก้ตัวแปร `EXCEL_FILE` และ `REF_DATE_STR` ในไฟล์ (ต้องเช็ค `MAX_STATUS_DATE` ล่าสุดใน AF sheet ก่อนเสมอ ไม่ใช่วันที่ upload) แล้วรัน `python3 update_data.py` — จะได้ `AF_new.json`/`NA_new.json`/`MN_new.json`/`ZM_new.json`/`RJ_new.json` พร้อมรายงานสรุปมาตรฐาน (ตรงกับหัวข้อ 9.1) พิมพ์ออกมาให้ตรวจสอบก่อนเขียนทับไฟล์จริง (สคริปต์ไม่ auto-patch `index.html` ให้ตั้งใจ เพื่อให้มีจังหวะตรวจสอบก่อนเสมอ)

⚠️ **แม้มี script แล้วก็ต้องตรวจสอบโครงสร้าง sheet ใหม่ทุกรอบ** (ชื่อคอลัมน์/ชื่อ sheet/ตำแหน่ง header อาจเปลี่ยนได้แบบไม่แจ้งล่วงหน้า อย่างที่เคยเจอมาแล้วหลายครั้ง — ดูหัวข้อ 8.1.1/8.1.2) ถ้าโครงสร้างเปลี่ยน ต้องแก้ script ให้ตรงก่อนรัน ไม่ใช่รันเชื่อ script เดิมแบบไม่เช็ค

ขั้นตอนด้านล่างคือ logic เดียวกับใน script อธิบายละเอียดเผื่อกรณีไม่มีไฟล์ script (session ใหม่ที่ไม่เห็น output เก่า) ต้องเขียนใหม่จาก README นี้:

### ขั้นตอน
1. **หา header row ของแต่ละ sheet** (ค้นหาด้วยคำ เช่น "รหัสลูกค้า", "ปรับสรุปการUPDATE" เพราะตำแหน่งอาจขยับ): AF (แถวที่ 3), สำหรับกรอง-ตรวจสอบ (แถวที่ 3), รายเดือน-ชน (แถวที่ 61 — เคยขยับมาแล้ว ต้องค้นหาใหม่ทุกครั้ง)
2. **Reconstruct mapping AF sheet → JSON field** ด้วยการเทียบ match rate กับข้อมูลเก่า (ใช้ cust ร่วมกัน) — ระวังจุดที่เคยพลาด:
   - `CONTRACT_DATE` เก็บปีเป็น **พ.ศ. ตรงๆ** (เช่น 2569) แต่ `DATE_01-11` เก็บเป็น **ค.ศ. ปกติ** (2026) — คนละ convention กันในคอลัมน์ datetime เดียวกันของชีตเดียวกัน! ใช้ auto-detect: `if (y < 2100) y += 543`
   - `due_last` มาจาก `Dueล่าสุด` (ตัวเลข YYYYMMDD, ค.ศ., ต้อง +543 หลังแปลง)
   - `due_amt`/`debt` ต้อง format comma 2 ตำแหน่งทศนิยม ไม่ใช่แค่ตัวเลขดิบ
   - `days_lag` = `REF_DATE - MAX_STATUS_DATE` (ไม่ใช่คอลัมน์ AGING_XX ตัวใดตัวหนึ่งตรงๆ)
   - `update` field: coalesce 3 ชั้น (ดูหัวข้อ 2) — ถ้าใช้แค่ `CUSTCARE_STATUS_NAME` อย่างเดียวจะได้ค่าว่างสำหรับกลุ่มไม่ดำเนินการ 143 รายการ
3. **สร้าง NA จาก "สำหรับกรอง-ตรวจสอบ" และ MN จาก "รายเดือน-ชน"** ตามหัวข้อ 1.1 (ห้าม filter จาก AF)
4. **Join `contract_type`** ใหม่ทั้ง 3 array ตามหัวข้อ 5
5. **ตรวจสอบบ้านเลขที่เพี้ยนเป็นวันที่** (ปัญหาที่รู้จักแล้ว, Google Sheets แปลงเลขบ้านแบบ `8/2` เป็นวันที่อัตโนมัติตอน paste จาก Excel) — ค้นด้วย pattern `^\d{4}-\d{2}-\d{2}` ในฟิลด์ `house` ทุกครั้ง ถ้าเจอให้แปลงกลับ (ดูตัวอย่างที่เคยแก้: cust 200199759 → "2/8" ยืนยันจาก number_format ในไฟล์ .xlsx ต้นฉบับ) — **ผู้ใช้รับทราบแล้วว่าจะไม่แก้ที่ต้นทาง Google Sheet ให้ dashboard แก้อัตโนมัติทุกรอบแทน**
6. **อัปเดตวันที่:** `UPDATE_BANNER` (update_data.py ทำให้) — `UPD_REF_DATE` คำนวณจาก banner เองแล้ว ห้ามกลับไปฮาร์ดโค้ด
7. **ตรวจสอบสมมติฐาน "no-op" ของ OVNA ใหม่** (หัวข้อ 4.3) และเช็คว่า NA/MN มี record ที่ progress ไปสถานะจริงกี่รายการ
8. **ห้ามแก้/ลบ** ฟังก์ชันในหัวข้อ 4 โดยไม่จำเป็น
9. **ตรวจสอบก่อนส่งกลับทุกครั้ง:**
   - JS syntax (`node -e "new Function(...)"`)
   - Column alignment: นับ `<th>` vs `<td>` ต่อแถว (ระวัง cell ที่ generate จากฟังก์ชัน เช่น `ckLagTd()` ไม่นับด้วย regex ธรรมดา ต้อง +1 ต่อจุดที่มี)
   - จำลอง filter สำคัญด้วย Python/Node เทียบข้อมูลจริง (pivot รวมคอลัมน์ = ยอดรวม, curStage/ckStatus/statusLagDays ยัง sync ถูกต้อง, join contract_type สำเร็จกี่ %)
   - ค้น `house` ทุก array ด้วย pattern `^\d{4}-\d{2}-\d{2}` (และรูปแบบผิดปกติอื่น เช่นมี `00:00:00` หรือยาวเกิน 15 ตัวอักษร) ทุกครั้งที่อัปเดตข้อมูลใหม่ — แม้รอบล่าสุด (18-08-69) จะไม่เจอเลยก็ตาม ปัญหานี้ขึ้นกับข้อมูลดิบแต่ละรอบ ไม่ใช่โค้ด จึงต้องเช็คซ้ำทุกรอบ
   - **ทดสอบจริงผ่าน jsdom** (จำลอง browser) ไม่ใช่แค่ตรวจ syntax — set filter, เรียก `ren*()`, เช็คค่าที่ render ออกมาจริง เทียบกับคำนวณอิสระด้วย Python/Node

```
af_status_lag,  // (RJ เท่านั้น) วันค้างของ af_status — ดูหัวข้อ 8.5
```
⚠️ **`o_letter`/`p_extra`/`q_appt` เป็น text อิสระจากสาขา** (เช่น "ครั้งที่ 2", "นัดหมายแล้ว", "ยังไม่ได้รับ") ไม่ใช่ true/false — ค่าว่างเปล่าเป็นเรื่องปกติมาก (ส่วนใหญ่ของข้อมูลจะว่าง) **ห้ามบีบเหลือแค่ 2 หมวด "มี/ไม่มี"** ต้องแสดงค่าจริงทั้งหมด (ดูหัวข้อ 8.2)

#### 8.1.1 `safe_start_con()` — วันทำสัญญามีได้ 2 รูปแบบดิบ ต้องเช็คทั้งคู่
เจอจริง: sheet "ซ่อมเสร็จ" คอลัมน์ "วันที่ทำสัญญา" เป็น **Excel serial number ดิบ** (`int64`, เช่น `244459`) แต่ sheet "ขอลดค่าซ่อม" คอลัมน์เดียวกันดันเป็น **datetime object ที่ parse มาแล้ว** (`datetime64[us]`) — ใช้ `pd.Timedelta(days=...)` บวกตรงๆ จะ **overflow เงียบๆ** (ค่าที่ได้ = ว่างเปล่า ไม่ error ชัดเจน) เพราะตัวเลข serial ระดับ 244,000+ วัน คูณ nanosecond ต่อวันแล้วเกิน int64
```python
def safe_start_con(v):
    if pd.isna(v): return ''
    if isinstance(v, (pd.Timestamp, datetime.datetime, datetime.date)):
        return dt_dmy_be(v)          # เป็น datetime อยู่แล้ว ใช้ตรงๆ
    try:
        dt = pd.to_datetime(v, origin='1899-12-30', unit='D')   # ต้องใช้ to_datetime ไม่ใช่ Timedelta บวกเอง
        return dt_dmy_be(dt)
    except Exception:
        return ''
```
**ต้องเช็ค `dtype` ของคอลัมน์นี้ทุกรอบอัปเดต** ทั้ง 2 sheet (`df['วันที่ทำสัญญา'].dtype`) ก่อนสมมติว่าเหมือนรอบก่อน

#### 8.1.2 `sheet_status` (RJ) — ห้าม hardcode ค่าคงที่เด็ดขาด
เคยพลาดมาแล้ว 1 ครั้ง: hardcode `rec['sheet_status'] = 'รอการจัดจ้าง'` เพราะตอนใช้ sheet "รอจัดจ้าง" ค่าคงที่จริงคือ "รอการจัดจ้าง" — พอ sheet เปลี่ยนชื่อเป็น "ขอลดค่าซ่อม" ค่าคงที่จริงกลายเป็น **"อนุมัติสรุปค่าก่อสร้าง"** (คนละสถานะ, คนละความหมาย) ทำให้ตอนเทียบกับ `af_status` (จาก AF) ได้ผลว่า "เปลี่ยนสถานะไปแล้ว 179/179" ทั้งที่จริง 0 รายการ — **badge สีในตารางก็เคย hardcode เทียบกับ string ตายตัวเหมือนกัน ต้องแก้คู่กัน:**
```python
# ✅ ถูกต้อง: อ่านค่าจริงจาก sheet ทุกครั้ง
rec['sheet_status'] = s(r.get('CUSTCARE_STATUS_NAME'))
```
```js
// ✅ ถูกต้อง: เทียบกับ x.sheet_status แบบไดนามิก ไม่ hardcode string
<span class="badge ${x.af_status && x.af_status!==x.sheet_status?'bgr':'bgy'}">
```
**หลักการทั่วไป:** ค่าคงที่ที่ "ดูเหมือนจะไม่เปลี่ยน" จาก sheet ใดๆ (เช่น CUSTCARE_STATUS_NAME ของ ซ่อมเสร็จ/ขอลดค่าซ่อม) **ต้องอ่านจากคอลัมน์จริงเสมอ ห้าม hardcode เป็น string ในโค้ด** แม้จะเช็คแล้วว่าตอนนี้คงที่จริง เพราะ sheet อาจเปลี่ยนชื่อ/ค่าฐานได้ในอนาคตโดยไม่แจ้งล่วงหน้า

### 8.4 Workflow อัปเดตข้อมูล — เพิ่มจากหัวข้อ 7 เดิม
ทุกครั้งที่ AF เปลี่ยน (ไม่ใช่แค่ AF/NA/MN):
1. **`contract_type` ของ ZM/RJ** ต้อง join จาก AF ใหม่ (มีแค่ใน sheet AF)
2. **`delivery_status` ของ ZM/RJ** ต้อง join รหัสลูกค้า → AF ใหม่ทุกครั้ง (พบ="ยังไม่ส่งมอบ", ไม่พบ="ส่งมอบแล้ว") — ลืมจุดนี้แล้ว donut "สถานะส่งมอบ" ทั้ง 2 sub-tab จะผิดทันที
3. **ตัว ZM/RJ เอง** ก็ต้องอ่านใหม่จาก sheet "ซ่อมเสร็จ"/"รอจัดจ้าง" ทุกรอบเช่นกัน (header แถวที่ 4 เสมอ ยืนยันแล้ว 2 รอบติด)
4. เช็คบ้านเลขที่เพี้ยนใน ZM/RJ ด้วย (pattern เดียวกับหัวข้อ 7 ข้อ 5)
5. **`status_lag` (ZM) และ `af_status`/`af_status_lag` (RJ)** ต้อง join จาก AF ใหม่ทุกครั้งเช่นกัน (ดูหัวข้อ 8.5 ว่าทำไมสำคัญ)
6. **`note` ของ AF** ต้อง join รหัสลูกค้า → sheet "สำหรับกรอง-ตรวจสอบ" ใหม่ทุกครั้ง (คอลัมน์ท้ายสุดของ sheet) — join เข้า AF โดยตรง ไม่ใช่แค่ NA เพื่อให้แท็บภาพรวม+ไม่ดำเนินการภาพรวมได้คอลัมน์ "หมายเหตุ" ด้วยอัตโนมัติ (OVNA derive จาก AF อยู่แล้ว)

### 8.5 คอลัมน์ตรวจจับความเปลี่ยนแปลง (`status_lag` / `af_status` / `af_status_lag`) — ทำไมสำคัญ

**คอลัมน์เหล่านี้เพิ่มมาเพื่อ "จับสัญญาณ" ว่า AF ขยับไปจากตอน snapshot หรือยัง โดยไม่ต้องรอสาขาส่ง sheet ชุดใหม่มาเทียบเอง:**

| Sub-tab | คอลัมน์ | ที่มา | สัญญาณที่บ่งบอกความเปลี่ยนแปลง |
|---|---|---|---|
| ดำเนินการเสร็จสิ้น (ZM) | `status_lag` ("วันค้างสถานะเสร็จสิ้น") | join AF, คำนวณวันค้างของ**สถานะปัจจุบันจริงใน AF** (ไม่ใช่ยึดติด "ดำเนินการเสร็จสิ้น" ตายตัว) | เลขสูงขึ้นเรื่อยๆ = ส่งมอบล่าช้า / คอลัมน์ `delivery_status` เปลี่ยนเป็น "ส่งมอบแล้ว" = หลุดจาก AF แล้ว (ส่งมอบสำเร็จ) |
| รอจัดจ้าง (RJ) | `sheet_status` | ค่าดิบจาก sheet "รอจัดจ้าง" เอง (คงที่ "รอการจัดจ้าง" เสมอ ไม่เปลี่ยนตาม AF) | ใช้เป็น baseline เทียบกับ `af_status` |

| รอจัดจ้าง (RJ) | `af_status_lag` | join AF, คำนวณวันค้างของ `af_status` | ใช้ดูว่าค้างสถานะใหม่นั้นมานานแค่ไหนแล้ว |

⚠️ **ข้อควรระวังตอนเขียนสคริปต์ Python สำหรับ join นี้:** อย่าเปิดไฟล์ `index.html` ด้วย `open(..., 'w')` ทิ้งไว้เฉยๆ ก่อนเขียนเนื้อหาจริง — จะเป็นการ truncate ไฟล์ทันทีตอนเปิด (เคยพลาดมาแล้วครั้งหนึ่ง กู้คืนจากไฟล์ที่เพิ่ง `present_files` ไปล่าสุดได้ทัน) ให้คำนวณ/เตรียมข้อมูลให้เสร็จก่อน แล้วค่อยเปิดเขียนเป็นขั้นตอนสุดท้ายเท่านั้น
