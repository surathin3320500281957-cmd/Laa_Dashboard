# คู่มืออ้างอิง: ที่มาของพิกัด (geo_method) ใน Dashboard พื้นที่จัดประโยชน์ กคช.

*(ไฟล์นี้ชื่อ `README.md` บน GitHub — ถูก render ขึ้นเป็นหน้าแรกของ repo อัตโนมัติ)*

เอกสารนี้อธิบายว่าพิกัด (lat/lng) ของแปลงที่ดินแต่ละแปลงในไฟล์ `data.json` (แท็บ "ที่ดิน 5 ไร่")
และ `lis_data.json` (แท็บ "ที่ดิน LIS") มาจากวิธีไหน สำหรับใช้อ้างอิงตอนอัปเดตข้อมูลในอนาคต

---

## 1. พิกัดเก็บอยู่ที่ไหน

**ไม่ได้เก็บในชีต `looker`** — ชีต looker มีแค่ข้อมูลดิบ (ชื่อโครงการ, เลขที่โฉนด, ที่อยู่, ลิงก์ Google Maps)

พิกัดจริง (`lat`, `lng`) เป็นค่าที่**คำนวณ/สืบค้นเพิ่มเติมภายหลัง** แล้วเก็บไว้ในไฟล์ **`data.json`**
(ไฟล์ข้อมูลของแท็บ "ที่ดิน 5 ไร่" แยกจาก `index.html`)

ทุกแปลงมี 2 ฟิลด์กำกับเสมอ:

| ฟิลด์ | ความหมาย |
|---|---|
| `lat`, `lng` | ตัวเลขพิกัด |
| `geo_method` | รหัสบอกว่าพิกัดนี้ได้มาจากวิธีไหน (ดูตารางข้อ 2) |
| `approx` | `true`/`false` — บอกว่าเป็นพิกัดโดยประมาณหรือแม่นยำ (Dashboard ใช้ฟิลด์นี้แสดงผล KPI "พิกัดแม่นยำ/โดยประมาณ") |

---

## 2. ตาราง geo_method ทั้งหมดที่ใช้อยู่

| geo_method | ที่มา | `approx` | ความแม่นยำ |
|---|---|---|---|
| `at_url` | ดึงพิกัดจากลิงก์ Google Maps แบบเต็ม (มี `@lat,lng` ในตัว URL) ที่กรอกไว้ในชีต looker คอลัมน์ "ตำแหน่งที่ตั้ง (google map)" | `false` | **แม่นยำ** — คนปักหมุดเองตรงตำแหน่งจริง |
| `q_param` | เหมือน `at_url` แต่ดึงจากพารามิเตอร์ `?q=lat,lng` ของลิงก์แทน | `false` | **แม่นยำ** |
| `lis_deed` | Join ข้อมูลกับไฟล์ V_LIS_TO_EIS ของกรมที่ดิน โดยจับคู่ด้วย เลขที่โฉนด + เลขที่ดิน แล้วแปลงพิกัด UTM (X,Y) เป็น lat/lng | `false` | **แม่นยำ** — เป็นพิกัดรังวัดจริงจากกรมที่ดิน |
| `landsmaps_manual` *(ที่เพิ่มจากสคริปต์ automation)* | ดึงจากเว็บ landsmaps.dol.go.th ด้วยสคริปต์ Python (Playwright) ค้นหาด้วยเลขที่โฉนด | `false` | **แม่นยำ** — มาจากฐานข้อมูลกรมที่ดินเช่นกัน (คนละช่องทางกับ lis_deed แต่ต้นตอเดียวกัน) |
| `approx_tambon` | หาทางอื่นไม่เจอ → ใช้พิกัดศูนย์กลางตำบล (จาก `loc_tambon`/`loc_amphoe`/`loc_changwat`) แทน | `true` | **โดยประมาณ** — คลาดเคลื่อนได้ตั้งแต่หลักร้อยเมตรถึงหลายกิโลเมตร ขึ้นกับขนาดตำบล |
| `approx_district` | เหมือน `approx_tambon` แต่ไม่มีข้อมูลตำบล เลยใช้ศูนย์กลางอำเภอแทน | `true` | **โดยประมาณ** — คลาดเคลื่อนมากกว่า approx_tambon |
| `approx_province` | ไม่มีข้อมูลอำเภอด้วย ใช้ศูนย์กลางจังหวัดแทน | `true` | **โดยประมาณมาก** — ใช้ดูภาพรวมเท่านั้น ไม่ควรใช้อ้างอิงตำแหน่งจริง |
| `unresolved` | หาพิกัดไม่ได้เลยแม้แต่ระดับจังหวัด | `true` | ไม่มีพิกัด (จำนวนน้อยมาก) |
| `needs_recheck` | เคย merge พิกัดผิดมาก่อน (เช่น ชนกับ deed_no ที่ซ้ำกันข้ามจังหวัด) แล้วถูกล้างคืนเป็นไม่มีพิกัด รอหาใหม่ | `true` | ไม่มีพิกัด — ต้องรันสคริปต์หาใหม่ในรอบถัดไป |

## 3. ลำดับการหาพิกัดที่ใช้อยู่ตอนนี้ (จากแม่นสุด → ประมาณสุด)

เวลาประมวลผลข้อมูลใหม่ ให้ลองตามลำดับนี้ก่อนเสมอ ก่อนจะยอมใช้ `approx_tambon`:

```
1. มีลิงก์ Google Maps เต็มในชีต looker?
   → ใช่ → ลองดึงพิกัดจาก URL (at_url / q_param)

2. ยังไม่มีพิกัด แต่มีเลขที่โฉนด + เลขที่ดิน ตรงกับ V_LIS_TO_EIS?
   → ใช่ → join เอาพิกัดจากตรงนั้น (lis_deed)

3. ยังไม่มีพิกัด แต่มีเลขที่โฉนด (แม้ไม่ตรงกับ V_LIS_TO_EIS)?
   → ใช่ → เข้าคิวรันสคริปต์ automation ค้นจาก landsmaps.dol.go.th (landsmaps_manual)

4. รันสคริปต์แล้วก็ยังไม่เจอ (deed ไม่มีพิกัดในระบบกรมที่ดินเลย)?
   → fallback เป็น approx_tambon/district/province ตามข้อมูลที่อยู่ที่มี
```

## 4. ⚠️ เมื่อได้ไฟล์ Excel เวอร์ชันใหม่ (รายเดือน) — ห้ามทำพิกัดที่หามาได้หาย

**สถานการณ์:** ไฟล์ Excel ที่ได้ทุกเดือนมี **2 ชีต** — `looker` (ข้อมูลแปลง กคช. ~1,617 แปลง) และ
`V_LIS_TO_EIS` (ฐานข้อมูลกรมที่ดินกว้างกว่า ใช้ทั้งสร้าง `lis_data.json` โดยตรง และใช้ join หาพิกัด
`lis_deed` ตอนสร้าง `data.json` ด้วย) **ทั้งสองชีตกระทบพิกัดที่สะสมไว้ทั้งคู่ ต้องระวังทั้งคู่**

**⚠️ อันตรายที่ต้องระวังที่สุด:** ถ้าสร้างไฟล์ใหม่ตาม pipeline เดิมล้วนๆ โดยไม่ทำอะไรเพิ่ม
**พิกัด `landsmaps_manual` ทั้งหมดที่สะสมมาจากสคริปต์ automation จะหายไปทันที ทั้งใน `data.json`
และ `lis_data.json`** เพราะพิกัดกลุ่มนี้ไม่ได้มาจากทั้งสองชีตเลย มันถูกหามาแยกต่างหากแล้วเก็บไว้ใน
ไฟล์ JSON เวอร์ชันปัจจุบันเท่านั้น **ห้ามสร้างไฟล์ใหม่ทับตรงๆ เด็ดขาดทั้งคู่**

### 4.1 ขั้นตอนที่ถูกต้องสำหรับชีต `looker` (สร้าง data.json ใหม่)

1. **สำรองพิกัดที่สะสมไว้ก่อน** — จาก `data.json` เวอร์ชันปัจจุบัน ดึงรายการที่ `geo_method == 'landsmaps_manual'`
   ทั้งหมด เก็บเป็น (deed_no, province, lat, lng) ไว้ต่างหาก **ก่อน**เริ่มประมวลผลไฟล์ Excel ใหม่
2. **สร้าง `data.json` ใหม่จากชีต looker เวอร์ชันใหม่** ตาม pipeline ปกติ (ข้อ 3: URL → lis_deed → approx_tambon)
   — ขั้นตอน `lis_deed` ในนี้ให้ใช้ชีต **`V_LIS_TO_EIS` เวอร์ชันใหม่** ด้วย (ดูข้อ 4.2 ประกอบ อาจได้ lis_deed
   เพิ่มขึ้นฟรีๆ ถ้ากรมที่ดินสำรวจพิกัดเพิ่มมาในเดือนนั้น)
3. **นำพิกัดที่สำรองไว้ในข้อ 1 กลับมาใส่คืน** โดย match ด้วย **`deed_no` + `province` เหมือนเดิมทุกประการ**
   (กฎเดียวกับข้อ 5 — ห้าม match แค่ deed_no เด็ดขาด กันปัญหาเลขโฉนดชนข้ามจังหวัด) — ใส่คืนทีหลังสุด
   เพื่อให้ `landsmaps_manual` (ข้อมูลยืนยันจริงจากเว็บ) มีสิทธิ์เหนือกว่า `lis_deed` เสมอถ้าชนกัน
4. **เช็คจำนวนแปลงที่ match สำเร็จ** ต้องได้ใกล้เคียง 119 (หรือจำนวนล่าสุดตอนนั้น) — **ถ้า match ได้น้อยกว่าที่ควร
   ห้ามข้ามไปเฉยๆ** ให้แจ้งว่ามีกี่แปลงที่ไม่ match (อาจเป็นเพราะเลขที่โฉนดถูกแก้ไขในชีตใหม่ หรือแปลงถูกลบออก)
   เพื่อให้ตรวจสอบด้วยตาก่อนตัดสินใจว่าจะทำอย่างไรกับแปลงเหล่านั้น
5. **เช็คจำนวนแปลงรวมทั้งหมด** เทียบกับเดือนก่อน — ถ้าจำนวนเปลี่ยนไป (ควรจะเท่าเดิมตามที่คาด) ให้แจ้งด้วยว่า
   เพิ่ม/ลดกี่แปลง เผื่อเป็นสัญญาณว่าโครงการใหม่เข้ามาหรือโครงการเก่าถูกปิดไป

### 4.2 ขั้นตอนที่ถูกต้องสำหรับชีต `V_LIS_TO_EIS` (สร้าง lis_data.json ใหม่)

**หลักการเดียวกับ looker เป๊ะ แค่สลับไฟล์:**
1. **สำรองพิกัดที่สะสมไว้ก่อน** — จาก `lis_data.json` เวอร์ชันปัจจุบัน ดึงรายการที่มี `lat` อยู่แล้ว
   ทั้งหมด (ทั้งที่มาจาก X,Y ใน V_LIS_TO_EIS เดิม และที่ sync มาจาก `landsmaps_manual`) เก็บ
   (deedno, province, lat, lng) ไว้ก่อน
2. **สร้าง `lis_data.json` ใหม่จากชีต V_LIS_TO_EIS เวอร์ชันใหม่** (แปลง UTM X,Y → lat/lng ตามปกติ)
3. **นำพิกัดที่สำรองไว้กลับมาใส่คืน** ด้วย `deedno` + `province` เหมือนเดิม — **แต่ต้องดูให้ดีว่าค่าใหม่จาก
   X,Y เวอร์ชันล่าสุดกับค่าที่สำรองไว้ตรงกันไหม** ถ้าต่างกันเล็กน้อย (กรมที่ดินรังวัดใหม่แม่นขึ้น) ให้ใช้
   **ค่าใหม่จาก V_LIS_TO_EIS แทน** (เพราะเป็นข้อมูลทางการล่าสุด) ยกเว้นแปลงที่ได้มาจาก `landsmaps_manual`
   sync (ไม่มี X,Y เดิมอยู่แล้วในไฟล์เก่า) ให้ใส่คืนตามปกติ
4. **เช็คจำนวนแถวรวมต้องเท่าเดิม** (เดิม 5,596 แถว — อาจเปลี่ยนได้ถ้ากรมที่ดินอัปเดตฐานข้อมูลเพิ่ม/ลด
   ให้แจ้งถ้าตัวเลขต่างจากเดิมมาก)

**ทำไมต้องระวัง 2 ชีตแยกกัน:** `looker` เปลี่ยน → กระทบ `data.json` เท่านั้น (โดยตรง) ส่วน
`V_LIS_TO_EIS` เปลี่ยน → กระทบทั้ง `lis_data.json` (โดยตรง) **และ** ขั้นตอน `lis_deed` ตอนสร้าง
`data.json` (โดยอ้อม) — ถ้าทั้งสองชีตเปลี่ยนพร้อมกันในไฟล์เดียว (กรณีปกติ) ต้องทำครบทั้งข้อ 4.1 และ 4.2

**สุดท้าย:** ทำครบทั้งสองข้อแล้ว **อย่าลืม sync ระหว่าง `data.json` กับ `lis_data.json` อีกรอบ** (ข้อ 5.5)
เผื่อมีพิกัดที่เพิ่งได้จาก `lis_deed` ใหม่ (ข้อ 4.1) ที่ยังไม่เคยอยู่ใน `lis_data.json` มาก่อน

**สรุปสั้นๆ:** ไฟล์ Excel ใหม่ทุกเดือน = จุดเสี่ยงทำพิกัดหายสูงสุด **ต้องสำรอง `landsmaps_manual`/พิกัดสะสม
ของทั้ง 2 ไฟล์ JSON ก่อนเสมอ แล้วค่อยเอากลับมาใส่คืนหลังสร้างไฟล์ใหม่เสร็จ** ไม่ใช่แค่รันสคริปต์เดิมซ้ำเฉยๆ

## 5. ขั้นตอน merge พิกัดใหม่เข้า data.json แบบละเอียด (⚠️ จุดเสี่ยงพลาดสุด — อ่านให้ครบก่อนทำ)

หลังรันสคริปต์ automation (เวอร์ชันล่าสุด `หาพิกัดจาก_landsmaps_v11.py`) เสร็จ จะได้ไฟล์ `ผลลัพธ์พิกัด.csv`
มีคอลัมน์: `province, district, deed_no, lat, lng, status, note`

**ห้ามเอาทุกแถวมา merge ตรงๆ** ต้องทำตามลำดับนี้เท่านั้น:

### ⚠️ คำเตือนสำคัญที่สุด: เลขที่โฉนดไม่ได้ไม่ซ้ำกันทั่วประเทศ!
เจอมาแล้วจริงในรอบที่ 2 — เลขที่โฉนด **66676** ตรงกับ 2 แปลงคนละจังหวัดกันโดยบังเอิญ
(เชียงใหม่ กับ กรุงเทพฯ) ถ้า merge ด้วยเลขที่โฉนดอย่างเดียว **จะใส่พิกัดผิดจังหวัดให้แปลงที่ไม่เกี่ยวข้องเลย**
โดยไม่มี error อะไรเตือนให้รู้ตัว (โค้ดรันผ่านปกติ แต่ข้อมูลผิด) — อันตรายกว่าไม่มีพิกัดเลยด้วยซ้ำ
**ต้อง match ด้วย `deed_no` + `province` (เทียบกับ `loc_changwat`) เสมอ ห้าม match แค่ deed_no เด็ดขาด**

### ขั้นตอน
1. **กรองเอาเฉพาะแถวที่ `status == found`** — แถวที่เป็น `timeout`/`error` ห้ามแตะข้อมูลเดิมเด็ดขาด (ปล่อย approx_tambon เดิมไว้)
2. **จับคู่กับ `data.json` ด้วย `deed_no` + `province` พร้อมกัน** (เทียบ CSV's `province` กับ `data.json`'s `loc_changwat`) — ระวังเรื่องชนิดข้อมูล: ใน `data.json` เป็นตัวเลข (`number`) แต่ในไฟล์ CSV เป็นข้อความ (`string`) ต้องแปลงให้ตรงกันก่อนเทียบ (เช่น `str(record['deed_no']) == csv_row['deed_no']`)
   - ถ้า match เจอมากกว่า 1 แปลงแม้จะเช็คจังหวัดแล้ว (กรณีหายากมาก) → **อย่า merge อัตโนมัติ** ให้แยกไว้เช็คมือ
3. **อัปเดตเฉพาะแปลงที่ตอนนี้ `approx == true` เท่านั้น** — กันเผลอทับพิกัดที่แม่นยำอยู่แล้ว
4. **อัปเดตพร้อมกันทั้ง 4 ฟิลด์ในแถวเดียว ห้ามอัปเดตแค่บางฟิลด์:**
   ```
   record.lat         = float(csv_row['lat'])
   record.lng         = float(csv_row['lng'])
   record.geo_method  = 'landsmaps_manual'
   record.approx      = false
   ```
5. **แปลงที่ไม่ได้อยู่ในผลลัพธ์ found เลย → ห้ามแตะฟิลด์ไหนทั้งสิ้น** (คงค่าเดิมไว้ทุกอย่าง)

### เช็คก่อนส่งไฟล์กลับ (checklist บังคับ)
- [ ] จำนวนแถวทั้งหมดใน `data.json` ยังเท่าเดิม (**1,617 แปลง** — ห้ามมีแปลงหายหรือเพิ่มขึ้น)
- [ ] จำนวนแปลงที่ `geo_method == 'landsmaps_manual'` ตรงกับจำนวน `found` ในไฟล์ผลลัพธ์พอดี (ไม่มากไม่น้อยกว่า — ถ้าเกิน แปลว่า match ซ้ำมากกว่า 1 แปลงต่อ 1 แถวผลลัพธ์ ต้องเช็คทันที)
- [ ] **เช็คว่าไม่มี deed_no ไหนที่ match แล้วโผล่มากกว่า 1 แปลงใน data.json** (โค้ดตรวจ: กลุ่มตาม deed_no แล้วนับ ถ้า >1 ต้องดูจังหวัดประกอบก่อน merge)
- [ ] สุ่มเช็ค 2-3 แปลงที่อัปเดต — เทียบเลขพิกัดใน `data.json` กับไฟล์ `ผลลัพธ์พิกัด.csv` ต้องตรงกันเป๊ะ **และเช็คจังหวัด/ที่ตั้งสมเหตุสมผล** (เช่น ไม่ใช่แปลงกรุงเทพฯ ที่ดันได้พิกัดเชียงใหม่)
- [ ] เปิดไฟล์ผ่าน JSON validator (หรือ `python3 -m json.tool`) ต้องไม่ error
- [ ] **หลัง merge เสร็จ ให้อัปเดตตาราง "ผลการรันสคริปต์" ในข้อ 6 ของเอกสารนี้ด้วยตัวเลขจริง**

### ไฟล์ที่ต้องอัปโหลดหลัง merge
**แค่ `data.json` ไฟล์เดียว** — ไม่ต้องแตะ `index.html`/`lis_data.json` เพราะรอบนี้แก้แค่ข้อมูล ไม่ได้แก้โค้ด
(ยกเว้นถ้าทำข้อ 5.5 ด้านล่างด้วย ให้อัปทั้งสองไฟล์คู่กัน)

## 5.5 การ sync พิกัดระหว่าง data.json กับ lis_data.json (สองแท็บคนละไฟล์ ไม่เชื่อมกันอัตโนมัติ)

**สำคัญ:** `data.json` (ที่ดิน 5 ไร่) กับ `lis_data.json` (ที่ดิน LIS) เป็นไฟล์ข้อมูลคนละไฟล์กัน
เวลาหาพิกัดใหม่ด้วยสคริปต์ automation แล้ว merge เข้า `data.json` ตามข้อ 5 —
**พิกัดนั้นจะไม่ปรากฏใน `lis_data.json` โดยอัตโนมัติ** แม้ว่าเลขที่โฉนดเดียวกันจะมีอยู่ในฐาน LIS ด้วยก็ตาม
(เป็นไปได้สูงเพราะฐาน LIS กว้างกว่าครอบคลุมแปลง กคช. อยู่แล้วบางส่วน)

ถ้าไม่ sync จะเกิดอาการไม่สอดคล้องกัน: แท็บ "ที่ดิน 5 ไร่" ขึ้นมีพิกัดแม่นยำ
แต่ค้นเลขที่โฉนดเดียวกันในแท็บ "ที่ดิน LIS" กลับขึ้น "ไม่มีพิกัด"

**วิธี sync (ควรทำเป็นระยะ เช่น ทุกครั้งที่พิกัดใน data.json เพิ่มขึ้นพอสมควร ไม่ต้องทำทุกวัน):**
1. หาแปลงทั้งหมดใน `data.json` ที่ `geo_method == 'landsmaps_manual'`
2. จับคู่กับ `lis_data.json` ด้วย **`deed_no` (จาก data.json) == `deedno` (จาก lis_data.json)
   และ `loc_changwat` (จาก data.json) == `province` (จาก lis_data.json)** — กฎ match ด้วยจังหวัดคู่กันเสมอ
   ใช้เหมือนข้อ 5 ทุกประการ (กันปัญหา deed_no ชนข้ามจังหวัดเหมือนกัน)
3. ถ้า match เจอ **และ** `lis_data.json`'s record นั้นยังไม่มี `lat` (เป็น `null`) → เติม `lat`/`lng` ให้
4. ถ้า `lis_data.json`'s record มี `lat` อยู่แล้ว (เช่น มี X,Y เดิมจาก V_LIS_TO_EIS อยู่แล้ว) → **ไม่ต้องแตะ** ปล่อยของเดิมไว้
5. เช็คจำนวนแถวทั้งหมดใน `lis_data.json` ต้องยังเป็น **5,596 แถวเท่าเดิม** ก่อนบันทึก
6. อัปโหลด `lis_data.json` คู่กับ `data.json` ขึ้น GitHub พร้อมกัน

**ผลการ sync ล่าสุด (ทำไปแล้ว):** เช็ค 119 แปลง `landsmaps_manual` ใน `data.json` เจอตรงกับ `lis_data.json`
102 แปลง — ในนั้น 96 แปลงยังไม่มีพิกัดมาก่อนจึงเติมให้ใหม่ ส่วนอีก 6 แปลงมีพิกัดอยู่แล้ว (ไม่แตะ)
ที่เหลือ 17 แปลงไม่มีเลขที่โฉนดตรงกันในฐาน LIS เลย (ปกติ เพราะฐาน LIS ไม่ครอบคลุมทุกแปลง)
→ `lis_data.json` มีพิกัดเพิ่มจาก 2,082 เป็น **2,189 แถว**

## 6. ผลการรันสคริปต์ automation ล่าสุด (บันทึกไว้อ้างอิง)

**รอบที่ 1 — ฐานข้อมูล LIS (แท็บ "ที่ดิน LIS", 5,596 รายการ)**
- ทดสอบ 1,023 แปลงที่ไม่มีพิกัดใน กทม./นนทบุรี/ปทุมธานี
- ผลลัพธ์: **found 11 (1.1%)**, timeout 976 (95.4%), error 36 (3.5%)
- สรุป: ส่วนใหญ่เป็นแปลงประกอบ/สาธารณูปโภค (ถนน, บ่อน้ำ, ที่ดินตะเข็บ) ที่ไม่เคยถูกรังวัดพิกัดในระบบกรมที่ดินเลยจริงๆ

**รอบที่ 2 — เจอปัญหา rate limit และค้นพบ "โควตารายวันต่อ IP" (จุดเปลี่ยนสำคัญ)**

ทดสอบกับ 621 แปลงของแท็บ "ที่ดิน 5 ไร่" ที่ยังเป็น approx — สรุปสิ่งที่ค้นพบระหว่างทาง:

1. **v8-v11**: ลองแก้หลายทาง (เพิ่มดีเลย์, พักยาว, รีสตาร์ตเบราว์เซอร์/เซสชันใหม่) แต่ทุกวิธี**ยังเจอ pattern เดิม**คือ found รัวๆ ~20-28 แปลงแรกแล้วเว็บเริ่มตอบ "ไม่พบ" ปลอมๆ (ไม่มี error, ไม่มี popup บัง เว็บแจ้งตรงๆ) — สรุปว่า**รีสตาร์ตเซสชัน/เบราว์เซอร์ไม่ช่วยอะไรเลย**
2. รันต่อเนื่องไปถึงแปลงที่ 187 ในวันเดียว → เว็บเริ่มบล็อกหนักขึ้นจนเปิดผ่านสคริปต์ไม่ได้เลย (`page.goto timeout`) ทั้งที่เปิดผ่าน Chrome ธรรมดายังปกติ
3. **✅ ค้นพบสำคัญ (ยืนยันแล้วหลายวัน):** โควตารีเซ็ตใหม่ทุกวัน ผูกกับ **IP + วันจริง** (ไม่ใช่ session/เบราว์เซอร์) — วันถัดไปทำงานได้ปกติทันทีโดยไม่ต้องรอ 1-2 วันแบบที่เคยสงสัยไว้ก่อนหน้า
4. **✅ ทดสอบยืนยันเพิ่มเติม:** ลองรันซ้ำ 2 รอบในวันเดียวกัน → **รอบที่ 2 ได้ 0/25 found ทันที** (โควตาวันนั้นถูกใช้ไปกับรอบแรกหมดแล้ว) ยืนยันชัดเจนว่าเป็นโควตาต่อวันจริงๆ ไม่ใช่ต่อการรันสคริปต์

**กลยุทธ์ที่ใช้อยู่ตอนนี้ (ได้ผลดีต่อเนื่อง):**
- รัน **20-25 แปลง/วัน/ครั้งเดียว** เท่านั้น (ห้ามรันซ้ำวันเดียวกัน เสียเวลาเปล่า)
- เก็บรายชื่อ deed_no ที่ `timeout` ไว้เป็นคิว **retry วันถัดไป** (ไม่ทิ้ง เพราะหลายแปลงที่เคย timeout กลับมา found ตอน retry — พิสูจน์แล้วว่าเป็นเพราะโดนตัดโควตา ไม่ใช่ไม่มีพิกัดจริง)
- **ถ้า timeout ติดกัน 3 รอบขึ้นไป (คนละวัน โควตาเต็มทุกครั้ง)** → สรุปว่าไม่มีพิกัดจริง ตัดออกจากคิว ไม่ต้องลองอีก (ประหยัดโควตาให้แปลงอื่น)

**ตัวอย่างที่ยืนยันแล้ว:** 6 แปลงกรุงเทพฯ (202390, 55117, 55122, 118556, 115483, 55118) timeout ครบ 3 รอบ → ตัดออกจากคิวแล้ว

**สถานะสะสมล่าสุด:** **119 แปลง** ได้พิกัดแม่นยำจาก `landsmaps_manual` แล้ว (ฝ่าย ชบ. เป็นหลัก) — sync เข้า `lis_data.json` แล้วด้วย (ดูข้อ 5.5)
คิว retry เหลือประมาณ **~94 แปลง** ในฝ่าย ชบ. (ทำไปแล้วเกินครึ่งของ 216 แปลงเริ่มต้น) ยังไม่เริ่มฝ่ายอื่น (ชอ./ชน./ชล./ชฉ./ชต. รวม ~382 แปลง)

**วิธีทำงานต่อในแต่ละวัน:**
1. ขอไฟล์ `input.csv` ใหม่จาก Claude (บอก "ขอ input.csv ชุดถัดไป 25 แปลงครับ") — จะได้ 25 แปลงที่ยังไม่เคย found สำเร็จ (คิว retry ก่อน แล้วค่อยแปลงใหม่ที่ไม่เคยลอง)
2. ลบ `ผลลัพธ์พิกัด.csv` เก่าทิ้งก่อนรันทุกครั้ง (กันสับสนกับผลวันก่อน)
3. รัน `python หาพิกัดจาก_landsmaps_v11.py`
4. ส่งไฟล์ `ผลลัพธ์พิกัด.csv` กลับให้ Claude merge เข้า `data.json`
5. อัปโหลด `data.json` (และ `lis_data.json` ถ้า sync ด้วย) ขึ้น GitHub
6. วันถัดไปวนซ้ำตั้งแต่ข้อ 1

## 7. ข้อควรระวังเรื่องคุณภาพข้อมูลต้นทาง

เจอปัญหาข้อมูลชื่ออำเภอ/ตำบลสะกดผิด หรือมีวงเล็บชื่อเก่าปนอยู่บ่อยครั้ง เช่น:
- `บางเขน(ตลาดขวัญ)` → ต้องตัดวงเล็บออกเหลือ `บางเขน`
- `เมืองแพร้่`, `สามาพราน`, `เมืองสมุุทรปราการ` → สะกดผิด ต้องแก้ก่อนใช้ค้นหา
- `เมือง` เฉยๆ (ไม่ระบุจังหวัด) → ต้องเติมชื่อจังหวัดต่อท้ายเอง เช่น `เมืองนนทบุรี`

**แนะนำ:** ทุกครั้งที่เตรียมไฟล์ input.csv ใหม่สำหรับรันสคริปต์ ควรเช็ครายชื่ออำเภอ/ตำบลที่ไม่ซ้ำ (`unique`) ก่อนเสมอ เพื่อจับจุดสะกดผิดก่อนรันจริง จะได้ไม่เสียเวลารันแล้วเจอ `error`

### เลขที่โฉนดไม่ได้ไม่ซ้ำกันทั่วประเทศ (สำคัญมาก — ทำให้ merge ผิดมาแล้วจริง)
เลขที่โฉนดซ้ำกันได้ระหว่างจังหวัด/อำเภอต่างกัน (พบเคสจริง: โฉนด 66676 มีทั้งที่เชียงใหม่และกรุงเทพฯ)
**ทุกครั้งที่ merge หรือค้นหาด้วยเลขที่โฉนด ต้องใช้คู่กับจังหวัด (และควรมีอำเภอด้วยยิ่งดี) เสมอ
ห้ามใช้เลขที่โฉนดเป็น key เดี่ยวๆ เด็ดขาด** — ดูรายละเอียดขั้นตอนที่ถูกต้องในข้อ 5

### เว็บ landsmaps.dol.go.th มีโควตารายวันต่อ IP (ยืนยันแล้ว ไม่ใช่แค่สงสัย)
พบว่าเว็บอนุญาตให้ค้นหาได้จริงแค่ **~20-25 ครั้ง/วัน/IP** เกินจากนี้จะเริ่มตอบ "ไม่พบ" ปลอมๆ
(ไม่มี error ไม่มี popup บัง ตอบตรงๆ ว่าไม่พบ) และถ้าฝืนรันต่อเนื่องยาวเกินไปในวันเดียว
อาจโดนบล็อกหนักขึ้นจนเปิดเว็บผ่านสคริปต์ไม่ได้เลย (แต่เปิดผ่าน Chrome ธรรมดายังปกติ)

**ข้อเท็จจริงที่ยืนยันแล้วจากการทดสอบหลายวัน:**
- โควตา**รีเซ็ตใหม่ทุกวัน** (ไม่ต้องรอ 1-2 วันแบบที่เคยคาดไว้ตอนแรก)
- โควตาผูกกับ **วันจริง ไม่ใช่ session/เบราว์เซอร์** — ปิด-เปิดเบราว์เซอร์ใหม่ในวันเดียวกัน **ไม่ช่วยรีเซ็ตโควตา**
- รันซ้ำ 2 รอบในวันเดียวกัน → รอบที่ 2 จะได้ found = 0 ทันที (ยืนยันแล้วจริง)

**กลยุทธ์ที่ใช้อยู่:** รัน **20-25 แปลง/วัน ครั้งเดียวเท่านั้น** เก็บ timeout ไว้ retry วันถัดไป
ถ้า timeout ครบ 3 รอบ (คนละวัน) ค่อยสรุปว่าไม่มีพิกัดจริง — ดูรายละเอียดเต็มในข้อ 6

มาใส่ในเว็บแบบ `data.json` **ต้องบอก Claude ให้แก้โค้ด HTML ตรงๆ ทั้ง 2 จุดข้างต้นพร้อมกันเสมอ**
(แก้จุดเดียวแล้วลืมอีกจุด จะทำให้ข้อมูลในหน้าเว็บกับใน PDF ไม่ตรงกัน)

**วิธีขอให้ถูกต้อง:** ส่งไฟล์ระเบียบเวอร์ชันใหม่ พร้อมบอกชัดเจนว่า "แก้เนื้อหาตารางเกณฑ์อำนาจอนุมัติทั้ง
2 จุดใน index.html ให้ตรงกับไฟล์นี้" — Claude จะอ่านไฟล์ สกัดเนื้อหา แล้วแก้โค้ดให้ตรงกันทั้ง 2 จุด

**ย้ำเรื่องความไม่ผูกมัด (ตามที่ตกลงกันไว้ตั้งแต่ต้น):** ตารางนี้เป็นข้อมูลอ้างอิงทั่วไปเท่านั้น
ไม่ใช่คำวินิจฉัยหรือคำแนะนำ ไม่ผูกกับแปลงใดเป็นการเฉพาะ การตัดสินใจขึ้นอยู่กับดุลยพินิจของผู้รับผิดชอบ
เสมอ — มีหมายเหตุนี้กำกับอยู่ท้ายตารางในหน้าเว็บอยู่แล้ว ไม่ต้องเพิ่มอะไรตรงนี้อีก
